RedSecReporter Guide

Building reports, proposals, and compliant PDF templates

This page documents how the Reporter builders work, how template rendering is split between document templates and section markdown, and which server-side values are available when building report and proposal designs.

Reports Proposals PDF Templates Markdown Sections Finding Templates Test Type Write-ups
Concepts

How Reporter content is assembled

RedSecReporter separates content from design. Reports and proposals store structured details, sections, findings, evidence, comments, and generated PDFs. Designs decide how those values are placed into the final PDF.

Report designs

Report designs are full HTML and CSS templates rendered server-side with Nunjucks. They receive a controlled context containing report, sections, findings, severity_counts, toc_items, annexures, members, evidence, and stats.

Proposal templates

Proposal document templates are also HTML and CSS, but each proposal section is normally markdown. Section markdown supports a deliberately limited placeholder set such as {{client_name}} and {{time_allocation_table}}. Unknown placeholders render as blank text.

Generated PDFs do not fetch remote assets. Use inline CSS, the provided {{ css | safe }} block, local Reporter image routes, or data URLs already produced by the renderer. Avoid external fonts, scripts, remote images, and browser-only JavaScript in templates.

Builder Workflow

Editing workflow and builder tools

Reports

  • Details feed the report.* values used on cover pages, metadata tables, executive summaries, and headers.
  • Members control team access and visible ownership inside the report workspace.
  • Sections are ordered markdown blocks. Executive summary and scope sections are promoted into report.executive_summary_html and report.scope_html.
  • Findings use the active design field schema. Markdown fields become finding.renderedFields for PDF output.
  • Evidence stores supporting files and images. Images can be inserted into markdown fields using the evidence insertion tool.
  • Notes, comments, history, and PDFs are operational records and review artefacts for the project.

Proposals

  • Details feed proposal placeholders, cover metadata, commercial terms, delivery schedule, and calculated totals.
  • Sections are markdown blocks rendered with the safe proposal placeholder set before markdown conversion.
  • Supporting Images uploads images to the proposal and inserts markdown image links into the selected section.
  • Notes, comments, history, and PDFs track internal preparation, review, and generated deliverables.
  • Test Type Write-ups provide reusable methodology, scope, deliverable, requirement, assumption, and restriction content for selected proposal types.

The live markdown preview uses the same server markdown renderer as PDF generation. For proposal placeholders, the final generated PDF applies placeholders first, then renders the markdown.

Markdown

Markdown section rules

Report sections, proposal sections, finding fields, finding templates, and test type write-ups use markdown. Supported formatting includes headings, paragraphs, bold, italic, inline code, fenced code blocks, blockquotes, unordered lists, ordered lists, task lists, links, images, horizontal rules, and markdown tables.

Recommended table format

Item | Value
-----|------
Estimated effort | {{estimated_days}} days
Total fee | {{quoted_value}}
Proposal valid until | {{valid_until}}

Use no outer pipe characters for simple tables. The renderer accepts normal markdown tables, but this shape avoids accidental blank edge columns.

Proposal placeholder example

## Client

**{{client_name}}**

**Primary Contact:** {{primary_contact_name}}{% if primary_contact_email %} ({{primary_contact_email}}){% endif %}

## Prepared By

{{prepared_by_name}}{% if prepared_by_email %} <{{prepared_by_email}}>{% endif %}

Proposal section placeholders are allowlisted names only. They do not execute arbitrary server expressions.

Reports

Report design templates: server-side values

PDF Design

Design compliance rules for PDF output

  • Target A4 print output with @page. Cover pages can use a named page with zero margins; content pages should leave enough margin for readable headers and footers.
  • Make internal table of contents links clickable with anchors: render each content section with id="{{ section.anchorId }}" and link to #{{ item.id }}.
  • Use CSS counters for section numbering instead of hardcoding numbers into section titles.
  • Do not add browser PDF headers or footers in the HTML. Any visual footer should be a deliberate part of the document design.
  • Keep scripts out of templates. PDF generation renders static HTML and blocks remote network requests.
  • Use server-rendered HTML fields with | safe; keep normal text values escaped.
  • Keep recurring components such as .running-header, .running-footer, .content-page, .page-break, .prose, and severity classes consistent across templates.
  • Use the details panel for client, prepared-by, date, duration, daily rate, allocation, and contact data. Do not duplicate those values as manually edited static text in sections.
  • For proposal service content, prefer test type write-ups and selected proposal types over manually copying methodology, scope, deliverables, requirements, assumptions, and restrictions into each proposal.
Security Boundary

Site CSP and preview rendering limitations

Reporter previews run inside the RedSecTools CSP and generated PDFs are rendered in a locked-down browser context. A template can look valid HTML and still fail if it depends on resources the site deliberately blocks.

HTML preview CSP

Embeddable HTML previews are served with a restrictive policy: default-src 'self', script-src 'none', style-src 'self', img-src 'self' data:, object-src 'none', base-uri 'self', and frame-ancestors 'self'.

This means no JavaScript, no external stylesheets, no remote images, no remote fonts, no third-party CDNs, and no inline event handlers.

PDF renderer network rules

PDF generation sets the document from server-rendered HTML and aborts network requests except about:blank and data: URLs. Proposal supporting images from /api/reporter/proposals/supporting-images/.../download are inlined by the renderer before PDF generation.

Use bundled CSS, inline CSS through {{ css | safe }}, local Reporter image routes, or data URLs. Do not import Google Fonts, Font Awesome, Bootstrap, external SVGs, CDN CSS, CDN scripts, or remote tracking pixels.

Compliant asset patterns

  • Use system fonts such as "Segoe UI", Arial, Helvetica, sans-serif unless a font is packaged and served by RedSecTools under a same-origin URL allowed by CSP.
  • Keep all document styling in the template CSS editor or the {{ css | safe }} style block generated by Reporter.
  • Use uploaded report evidence or proposal supporting images for images that need to appear in a PDF.
  • Use CSS shapes, borders, counters, and tables for layout. Do not depend on client-side scripts to build or modify the PDF DOM.
  • If preview shows missing styling or blank media, check for blocked external URLs before changing CSP. The correct fix is normally to make the design self-contained.
Reuse

Finding templates and test type write-ups

Finding templates

Finding templates are reusable finding records. They store a title, category, severity, optional CVSS vector, tags, and markdown content for each finding field configured by the active report design. Use them to standardise common vulnerability language without changing the report design.

Test type write-ups

Test type write-ups are reusable proposal content keyed by assessment type. They can provide methodology, scope, deliverables, client requirements, consultant requirements, assumptions, and restrictions. Proposal templates can render those fields from test_types[] so selected proposal types automatically pull the matching content.
